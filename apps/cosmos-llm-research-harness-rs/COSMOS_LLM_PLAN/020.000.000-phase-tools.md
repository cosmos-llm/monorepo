# Phase 020 — Tool layer

`cosmos-llm-tool` has the right pieces — `ToolDefinition`, `Registry`, `Executor`,
`Parameter`, `schemas`, and preset tools. Two things block the harness.

**Exit criteria:** an async tool-calling loop runs end to end against the mock
provider, with tool results correctly attributed back to their calls.

## The two blockers, stated plainly

**`Executor::execute` is synchronous.** Signature:
`fn execute(tool: &ToolDefinition, params: &Value) -> Result<Value, ToolError>`.
Every research tool does network or disk I/O. A synchronous handler inside an async
agent loop either blocks the runtime or gets wrapped in `spawn_blocking`, and
`spawn_blocking` around an `async` HTTP client is not a workaround — it is a
deadlock waiting for load.

The `webfetch` preset already hits this: it is feature-gated on `tokio` and has to
construct or borrow a runtime to do an async fetch from a sync function.

**`Message` has no `tool_call_id`.** `cosmos_llm::types::Message` is `{ role,
content }`. Both OpenAI and Anthropic require tool results to reference the call
they answer. Without it, a multi-tool turn cannot be replied to correctly — the
provider cannot tell which result belongs to which call, and with parallel tool
calls that is not recoverable.

These are the two things that make the difference between "the harness can be
built" and "the harness cannot be built".
