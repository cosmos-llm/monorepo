# 010.030 — Capability reporting

## Why

Consumers branch on what a provider can do. Today the only signal is
`supports_streaming()`. The harness needs more: whether tools work, whether system
messages are accepted, what the context window is.

Getting this wrong produces the worst class of LLM bug — a request that is accepted
and answered, but wrong, because a feature was silently ignored.

## Microsteps

### 010.030.010 — `Capabilities`

```rust
#[non_exhaustive]
pub struct Capabilities {
    pub streaming: bool,
    pub tools: bool,
    pub parallel_tool_calls: bool,
    pub embeddings: bool,
    pub vision: bool,
    pub json_mode: bool,
    pub system_message: SystemMessageSupport,  // Native | AsFirstUser | Unsupported
    pub prompt_caching: bool,
}
```

`SystemMessageSupport` is an enum, not a bool, because the three cases need
different handling and collapsing them loses the distinction that matters.

### 010.030.020 — Provider-level and model-level

Capabilities differ per model within one provider — OpenAI has vision and
non-vision models. `Provider::capabilities()` reports the provider's ceiling;
`ModelInfo::capabilities` reports a specific model's.

A consumer checks the model when it knows one, the provider when it does not.

### 010.030.030 — Honest reporting

Same rule the existing `supports_streaming` doc states: report what the
implementation *does*, not what the upstream API offers. A provider whose tool
support is unimplemented reports `tools: false` even though the vendor's API has
it.

This is the difference between "this crate does not do it yet" and "your request
will silently do the wrong thing", and consumers can only act on the first if we
are honest about it.

### 010.030.040 — Deprecate, do not break

`supports_streaming()` becomes a default method returning
`self.capabilities().streaming`, marked `#[deprecated]`. Existing callers keep
working through at least one minor release.

### 010.030.050 — Preflight validation

`Client` gains a check: a request with tools sent to a provider reporting
`tools: false` fails before the network call, with a message naming the provider
and the missing capability.

Cheaper than a confusing provider-side error, and much cheaper than a response
that ignored the tools and answered from memory.

## Verification

- Each provider's reported capabilities match what its tests demonstrate.
- Preflight rejects a tools request to a non-tools provider without a network call.
- The deprecated shim returns the same value as before for all three providers.
