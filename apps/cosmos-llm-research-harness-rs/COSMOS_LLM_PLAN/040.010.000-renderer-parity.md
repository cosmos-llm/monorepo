# 040.010 — Renderer parity and registry

## Microsteps

### 040.010.010 — Audit against Ruby

Compare `cosmos-llm-rust-context/src/renderers.rs` against
`lib/ruby/cosmos-llm-ruby-context/lib/cosmos/llm/context/renderers/`. Ruby has
five: default, xml, json, anthropic, openai.

For each, verify the Rust version exists and produces equivalent output for the
same input. Write cross-language golden files — one fixture context, rendered by
both, compared. Where they differ, decide which is correct and fix the other.

This is tedious and it is the point of the phase. Two clients that render the same
context differently produce different model behavior, and nobody will suspect the
renderer.

### 040.010.020 — Renderer registry

Convert `RenderFormat` from an enum to a `RendererEntry` registry per
[`../PLAN/005.010`](../PLAN/005.010.000-plugin-registry-pattern.md).

Keep an enum-shaped convenience API for the built-ins so existing callers do not
break, with the registry underneath.

### 040.010.030 — Renderer selection by provider

A helper mapping provider name to its preferred renderer: anthropic → xml,
openai → the openai renderer, unknown → default.

Anthropic's models respond measurably better to XML-delimited context; OpenAI's to
markdown structure. This is free quality if the plumbing picks correctly, and lost
if every consumer has to know to pick.

### 040.010.040 — Renderer output is a prompt

Same rule as tool descriptions. A renderer change alters every prompt every
consumer sends. Snapshot-test all of them so a change is visible in review, and
treat renderer edits as behavior changes rather than formatting cleanups.

### 040.010.050 — Message-list output, not just a string

`render` returns a `String`. Providers take a message list, and the mapping from
blocks to messages is not always "concatenate everything into one system message" —
history blocks should become individual messages with their own roles.

Add `render_messages() -> Vec<Message>` alongside `render()`. The harness needs it
([`../PLAN/030.020`](../PLAN/030.020.000-context-assembly.md)), and doing it in the
context crate means every consumer gets correct role attribution instead of
reimplementing it.

## Verification

- Cross-language golden files match for all five renderers.
- `render_messages` produces correct roles for a context with history.
- Provider-preferred renderer selection covers every registered provider.
- A test-registered renderer is selectable by name.
