# Phase 040 — Context building

`cosmos-llm-context` has `ContextBuilder`, `Block`, `RenderFormat`, and virtual
filesystem attachment. Close to what the harness needs.

**Exit criteria:** renderer parity with Ruby, real token counting, and
budget-aware assembly that trims deterministically.

## Steps

- [040.010](040.010.000-renderer-parity.md) — Renderer set and registry
- [040.020](040.020.000-budget.md) — Budget-aware assembly and trimming
- [040.030](040.030.000-token-counting.md) — `llm-token-estimate` (layer 2)

## Current gaps

**Renderer coverage unverified.** Ruby ships five renderers — default, xml, json,
anthropic, openai. Rust has a `RenderFormat` enum; confirm it covers the same set
and produces equivalent output. A prompt that renders differently in Ruby and Rust
means the two clients get different results from the same model, which is a
difficult bug to even notice.

**No token awareness.** `ContextBuilder::render` returns a `String` with no notion
of budget. Every consumer that needs to fit a context window writes its own
trimming, and each one does it differently.

**Renderers are an enum, not a registry.** Should be a registry per
[`../PLAN/005.010`](../PLAN/005.010.000-plugin-registry-pattern.md) — a user with a
provider needing a particular prompt shape should be able to add a renderer.

## Note on ordering

Blocks render in insertion order, which makes prompt prefixes stable and
provider-side prompt caching effective. Confirm that ordering is guaranteed and
documented — if it depends on a `HashMap` anywhere, caching silently stops working
and nobody notices except in the bill.
