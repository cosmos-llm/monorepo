# 020.030 — Registry-based tool discovery

## Current state

`Registry` is a runtime `HashMap<String, ToolDefinition>` populated by explicit
`register` calls. That is correct and stays — per-instance registration is needed
for tools configured at runtime.

What is missing is *static* discovery: a way for a preset or a third-party crate to
make a tool available without the consumer knowing it exists.

## Microsteps

### 020.030.010 — `ToolEntry`

```rust
pub struct ToolEntry {
    pub name: &'static str,
    pub description: &'static str,
    /// Category, for grouping in listings. Free-form.
    pub category: &'static str,
    pub priority: i32,
    pub make: fn() -> ToolDefinition,
}

durable_inventory::collect!(ToolEntry);
```

Presets submit entries. `Registry::with_defaults()` populates from the collected
set; `Registry::new()` stays empty for consumers who want explicit control.

Both are needed. Static registration supplies what is compiled in; runtime
`register` adds what is configured. Neither replaces the other.

### 020.030.020 — Feature-gated presets still register correctly

`webfetch` is behind a feature. Its `submit!` sits inside the same `#[cfg]`, so a
consumer without the feature does not get a broken entry. Verify this — a
registration referencing a `make` function that does not exist is a link error, and
a confusing one.

### 020.030.030 — Tool descriptions are prompts

Restating from [`../PLAN/030.040.070`](../PLAN/030.040.000-tools.md) because it
applies to the presets too: a tool's `description` and parameter docs are read by
the model and largely determine whether it gets used correctly.

Review the existing preset descriptions with that in mind. Snapshot-test them so an
edit is visible in review.

### 020.030.040 — Listing and introspection

`tools::list()`, `tools::find(name)`, `tools::by_category(c)`. These let a CLI
print available tools and let an MCP server project the registry into a tool list
([`../PLAN/deferred/mcp.md`](../PLAN/deferred/mcp.md)) rather than maintaining a
second set of definitions.

### 020.030.045 — Port the four missing presets

Ruby ships twelve presets: read, write, list, grep, glob, diff, patch, exec, jq,
webfetch. Rust ships six: read, write, glob, grep, list, webfetch.

Missing: **diff, patch, exec, jq**. Port them with Ruby's names and parameter
schemas ([005](005.000.000-ruby-parity-principle.md)).

`exec` runs subprocesses. It carries real capability, so it ships behind a feature
flag, off by default, and consumers that enable it must gate it through a
permission model — the same posture the harness applies to custom tools
([`../PLAN/030.040.080`](../PLAN/030.040.000-tools.md)). Check what Ruby's version
does about argument escaping before porting; if it shells out through a string,
the Rust version should not copy that.

Also confirm the Ruby definitions of the six shared presets match the Rust ones —
same parameter names, same defaults. A `grep` tool whose `pattern` parameter is
called `query` in the other language is a silent portability trap.

### 020.030.050 — Schema generation for the provider

`ToolDefinition` → the JSON the provider expects in its `tools` array. Per-provider,
because Gemini's dialect differs ([010.050.010](010.050.000-google.md)). One
function per provider, tested against fixtures.

## Verification

- `Registry::with_defaults()` contains every preset compiled in.
- `--no-default-features` yields a registry without `webfetch` and no link errors.
- A test-submitted entry is discoverable and can shadow a preset by priority.
- Generated schemas validate against each provider's documented format.
