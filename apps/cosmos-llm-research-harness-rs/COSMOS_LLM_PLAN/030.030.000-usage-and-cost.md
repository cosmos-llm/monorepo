# 030.030 — Usage accounting and cost

Ruby's `ResponseHelpers` already provides `extract_content`, `all_contents`,
`token_usage`, `finish_reason`, `truncated?`, `to_hash`, `model_used`, and
`estimate_cost`. Rust has a `Usage` struct and nothing that interprets it.

Mirror those names ([005](005.000.000-ruby-parity-principle.md)). Rust's
`CompletionResponse` already covers `content()` and `text()`; add the rest —
`token_usage()`, `finish_reason()`, `truncated()`, `model_used()`, `estimate_cost()`.

Read Ruby's `estimate_cost` before designing the price table below. If it already
carries pricing data, share the data file across languages rather than maintaining
two that will disagree.

## Why it matters here

An agentic research tool makes many calls per query — a twenty-turn loop with tool
results is twenty completions. Users need to know what a query cost, and Plan mode
([`../PLAN/030.030.050`](../PLAN/030.030.000-agent-loop.md)) needs to estimate it
before spending.

## Microsteps

### 030.030.010 — Usage from streaming

Non-streaming responses carry usage. Streaming often does not, or carries it only
in a final chunk that some providers omit by default (OpenAI needs
`stream_options: {include_usage: true}`).

`StreamAccumulator::usage()` exists. Verify it populates for every provider, and
where a provider will not report it, fall back to an estimate from
`llm-token-estimate` — clearly marked as an estimate, not a measurement.

### 030.030.020 — Cumulative accounting

```rust
pub struct UsageLedger {
    entries: Vec<UsageEntry>,   // provider, model, usage, timestamp
}
impl UsageLedger {
    pub fn total_tokens(&self) -> u64;
    pub fn by_model(&self) -> BTreeMap<String, Usage>;
    pub fn cost(&self, prices: &PriceTable) -> Option<Cost>;
}
```

A ledger, not a running total, because "which model spent the money" is the
question people actually ask.

### 030.030.030 — The price table problem

Prices change, vary by region and tier, and no provider offers a reliable pricing
API. A hardcoded table goes stale and then lies.

Approach:
- Ship a table with an explicit `as_of` date.
- Every cost figure is labeled with that date.
- Allow a user-supplied table to override.
- When a model is not in the table, return `None` — **never** guess.

`Option<Cost>` throughout. A wrong cost figure is worse than no figure, because
people budget against it.

### 030.030.040 — Where the price table lives

Not in `cosmos-llm`. A price table is data with a shelf life, and putting it in a
library means a release every time a vendor changes a price.

A separate `cosmos-llm-pricing` crate that can be versioned on its own schedule,
with the table as a data file and a loader for user overrides.

### 030.030.050 — Cached and free tokens

Prompt caching changes the arithmetic — cached input tokens cost a fraction. Usage
should distinguish cached from fresh input tokens where the provider reports it
(Anthropic and OpenAI both do), or the cost is overstated for exactly the workload
that benefits most from caching.

### 030.030.060 — Estimation before spending

`estimate(request, price_table) -> Option<CostRange>`. Input tokens are countable
before the call; output is a range from `max_tokens` and a typical-length heuristic.

A range, not a point. A point estimate for output length is a fiction.

## Verification

- Usage populates for every provider, streaming and not.
- Ledger totals match the sum of entries.
- An unknown model returns `None`, never a guess.
- Cost output includes the price table's `as_of` date.
- Cached-token accounting matches a recorded Anthropic response with cache hits.
