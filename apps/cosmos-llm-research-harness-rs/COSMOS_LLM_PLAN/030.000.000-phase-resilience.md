# Phase 030 — Resilience, usage, and cost

Retry, fallback, error classification, and token accounting. All of it belongs in
`cosmos-llm`, not in the harness — every consumer needs it, and the old TypeScript
proved what happens when each application writes its own.

**Exit criteria:** a transient failure retries with sensible backoff, a persistent
one falls back, and every response carries usage the caller can turn into a cost.

## Steps

- [030.010](030.010.000-retry.md) — Error classification and retry with backoff
- [030.020](030.020.000-fallback.md) — Provider fallback chains
- [030.030](030.030.000-usage-and-cost.md) — Usage accounting and pricing

## Why this is not the harness's job

`Researcher.research()` in the old code is 1,205 lines, and a large share of it is
provider retry and fallback logic interleaved with research logic. It is
untestable in that position, and the JS and Ruby clients each have their own
version of the same thing.

A retry policy is a property of talking to an LLM API, not of doing research. Put
it where every consumer gets it.

## Design constraint

Retry, fallback, and caching interact badly if each is written independently:

- Retrying inside a fallback chain that also retries multiplies attempts.
- Caching a failed response turns a transient error into a persistent one.
- Retrying a request that a cache would have served wastes the retry budget.

Design them together, document the interaction, and give the composed behavior a
test. The harness's own layering note
([`../PLAN/070.030.040`](../PLAN/070.030.000-activities.md)) makes the same point
about gearwork's memoization.
