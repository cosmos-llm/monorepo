# 005 — Ruby parity principle

Read this before any phase file in this directory. It constrains every API design
here, and it changes several designs those files currently propose.

## The rule

**The Rust crates mirror the Ruby gems as closely as is reasonable.** Same
concepts, same names, same method shapes, same error taxonomy, same environment
variables, same provider names. Idiom differs; the model does not.

"As closely as is reasonable" carves out genuine language differences — ownership,
futures vs. threads, `Result` vs. exceptions. It does not carve out "I preferred a
different name."

## Why this is a constraint and not a preference

Ruby is the primary language in this monorepo and its client is the most complete
implementation: 16 providers to Rust's 3, a full error hierarchy, response
helpers with cost estimation, and — the thing worth noticing — an **agent loop
that already exists** (`cosmos-llm-ruby-tool/lib/cosmos/llm/tool/loop.rb`).

That loop's own documentation says it generalizes code "app-local code has
reimplemented more than once (e.g. cosmos-llm-researcher's
`CosmosLlmResearcher::Llm#run_tool_loop`)." Somebody already learned the lesson
this plan is built around. Rust should inherit the conclusion, not repeat the
detour.

Three practical payoffs:

1. **Design work is already done.** Where Ruby has a working API, Rust ports it
   instead of inventing one. Faster, and the design has seen use.
2. **Behavior stays consistent.** A team running both against one deployment gets
   the same results, the same errors, and the same config.
3. **The later ports get easier.** Crystal and JS clients exist too. A shared
   conceptual model across four languages is only achievable if it is enforced from
   the start.

## What Ruby already has that Rust does not

Audited against `lib/ruby/`. Each of these changes a plan item in this directory.

### The agent loop — `Cosmos::Llm::Tool::Loop`

186 lines. `Loop.run(client:, tools:, user:, system:, max_steps:, schema:, &dispatch)`
returning `{ text:, steps_taken: }`. Normalizes tool calls across providers,
dispatches through a `Registry` keyed by tool name, appends results, repeats until
the model stops calling tools or `max_steps` is hit. A block overrides registry
dispatch.

**Impact on [070.010](070.010.000-agent-crate.md):** `cosmos-llm-agent` is a *port
plus extension*, not a new design. Port the loop's shape first — `run`, the
`max_steps` cap, the normalized `ToolCall { id, name, input }`, the
registry-or-block dispatch. Then add what Rust needs and Ruby lacks: cancellation,
event emission, permissions, concurrent dispatch.

Feed those extensions back to Ruby ([080](080.000.000-phase-ruby-parity.md)) rather
than letting the two diverge.

The Ruby loop's stated limitation — it builds Anthropic-format content-block
messages and does not support providers that lack `tool_use?`/`tool_calls`/`text` —
is exactly what [020.020](020.020.000-tool-messages.md) fixes in Rust. Fix it in
both.

### The provider-neutral response shape

Ruby responses answer `tool_use?`, `tool_calls` (→ `[{id, name, input}]`), and
`text`. Rust's `CompletionResponse` already has `tool_use()`, `tool_calls()`,
`text()`, and `content()`. **These already match** — preserve that. Do not rename
them during any refactor in this plan.

### The error hierarchy

Ruby has twelve error classes under a base `Error`: `APIError`, `RateLimitError`,
`AuthenticationError`, `InvalidRequestError`, `ResourceNotFoundError`,
`TimeoutError`, `ServerError`, `UnsupportedProviderError`, `ConfigurationError`,
`ModelNotFoundError`, `InsufficientQuotaError`, `InvalidResponseError`,
`NetworkError`, `StreamingError`.

**Impact on [030.010.010](030.010.000-retry.md):** that step proposes a new
classification. Replace the proposal with Ruby's taxonomy, translated to variants.
Ruby's set is broader and battle-tested — `InsufficientQuotaError` and
`ModelNotFoundError` are conditions my proposed set folded into vaguer variants,
and both are worth distinguishing because a caller can act on them.

Rust adds `is_retryable()` and `retry_after()`, which Ruby lacks. Add the
equivalent to Ruby ([080.020](080.000.000-phase-ruby-parity.md)) — probably a
`retryable?` predicate on the base class.

Two Rust-side variants have no Ruby equivalent and are worth keeping:
`ContextLength` (callers can trim and retry) and `ContentFiltered`. Add them to
Ruby too.

### Response helpers

`ResponseHelpers` provides `extract_content`, `all_contents`, `token_usage`,
`finish_reason`, `truncated?`, `to_hash`, `model_used`, `estimate_cost`.

**Impact on [030.030](030.030.000-usage-and-cost.md):** the usage and cost work
should mirror these names. `estimate_cost` already exists in Ruby — check what
price table it uses before designing `cosmos-llm-pricing`, and share the data file
between languages if the format allows.

### The client's fluent builders

Ruby's `Client` has `with_provider`, `with_model`, `with_temperature`,
`with_max_tokens`, `with_tools`, `with_tool_choice`, `with_system`, `with_top_p`,
`with_stop`, and `clone_with`.

Rust has `with_model`, `with_provider`, `with_provider_at`. The gap is real: a Rust
caller sets temperature on the `CompletionRequest`, a Ruby caller on the client.

**Add the missing builders to Rust's `Client`**, matching Ruby's names, as
per-client defaults that a request can override. Not currently in any phase file;
schedule it in [010.010](010.010.000-trait-review.md).

### `embed` / `embedding`

Ruby's `Client#embed` and `Providers::Base#embedding`. Rust has neither.
[010.010.020](010.010.000-trait-review.md) already schedules this. Match the Ruby
names: `Client::embed`, `Provider::embedding`.

### Tool presets

Ruby ships twelve presets: read, write, list, grep, glob, diff, patch, exec, jq,
webfetch. Rust ships six: read, write, glob, grep, list, webfetch.

Missing in Rust: `diff`, `patch`, `exec`, `jq`. Port them, matching names and
parameter schemas. Note `exec` runs subprocesses — it should carry the same
permission posture the harness applies to custom tools
([`../PLAN/030.040.080`](../PLAN/030.040.000-tools.md)).

### Context renderers

Ruby has five renderer files: `anthropic_renderer`, `default_renderer`,
`json_renderer`, `openai_renderer`, `xml_renderer`. This confirms the count
[040.010.010](040.010.000-renderer-parity.md) assumed. Cross-language golden files
are the verification.

## The environment variable divergence

Ruby's `configuration.rb` documents `CLLM__` and uses it in `load_from_env`. But
`providers/base.rb:254` and three places in `cli.rb` still emit `DLLM__` — the
older `durable-llm` prefix.

**Resolution: `CLLM__` is canonical in both languages.** Ruby's own configuration
loader already treats it that way; the `DLLM__` occurrences are leftovers from the
rename. Accept `DLLM__` as a deprecated alias with a warning, in both languages,
and fix the Ruby strings that still print it.

The harness uses `CLLM_RESEARCH__` for its own settings
([`../PLAN/010.050.030`](../PLAN/010.050.000-config.md)) and delegates provider
keys to `cosmos-llm`, so it inherits whatever this resolves to.

## Where Rust should lead

Parity is not one-directional. Rust has things Ruby should take:

| Rust has | Ruby should get |
|---|---|
| `StreamAccumulator` rebuilding a full response from chunks, including tool calls | The same, so a streaming tool loop works in Ruby |
| `stream_from_response` factoring shared SSE plumbing | Equivalent shared decoding |
| `Client::new_with_base_url` for OpenAI-compatible endpoints | Ruby has per-provider classes; a base-URL override collapses several |
| `supports_streaming` reporting implementation, not vendor capability | Honest capability reporting |
| `#[non_exhaustive]` discipline | N/A — Ruby has no equivalent problem |

When a Rust design here is better than Ruby's, say so in the plan file and schedule
the Ruby change in [080](080.000.000-phase-ruby-parity.md). Divergence is
acceptable *as a recorded decision*, never as drift.

## What is allowed to differ

- **Concurrency.** Futures and `Send + Sync` bounds in Rust; threads and blocks in
  Ruby. `Loop.run`'s `&dispatch` block becomes a trait or closure parameter.
- **Errors.** `Result<T, E>` vs. raised exceptions. The *taxonomy* matches; the
  mechanism does not.
- **Registration.** `durable-inventory` in Rust, `Class#inherited` plus Zeitwerk in
  Ruby ([050.040](050.000.000-phase-registries.md)). Same semantics — `find(name)`,
  `list`, priority override, visible shadowing.
- **Naming case.** `with_model` in both, but `tool_use?` becomes `tool_use()`.
  Ruby's `?` and `!` suffixes have no Rust equivalent; drop them, keep the stem.
- **Builders returning self.** Ruby's `with_*` methods return a cloned client
  (`clone_with`); Rust's take `mut self` and return `Self`. Same ergonomics,
  different ownership.

## Working rule

When designing anything in this directory, open the Ruby equivalent first. If one
exists, port it. If none exists, design it so it *could* be ported — and if it
could not be expressed idiomatically in Ruby, treat that as evidence the design is
over-fitted to Rust.

Concretely: `grep -rn "def " lib/ruby/cosmos-llm-ruby-*/lib` before writing a new
public API.
