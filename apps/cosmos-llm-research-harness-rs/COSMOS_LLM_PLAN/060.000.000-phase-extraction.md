# Phase 060 — Extracting the generic layers

Pull logic that is not LLM-specific out of the Cosmos-LLM crates into standalone
crates with their own audiences, per
[`../PLAN/005`](../PLAN/005.000.000-decomposition-principle.md).

**Exit criteria:** each extracted crate builds, tests, and documents without any
`cosmos-llm` dependency, and the parent crate depends on it with no behavior change.

## Steps

- [060.010](060.010.000-extract-sse.md) — `sse-decode` from `cosmos-llm/src/sse.rs`
- 060.020 — `retry-policy`, specified in [030.010.020](030.010.000-retry.md)
- 060.030 — `llm-token-estimate`, specified in [040.030](040.030.000-token-counting.md)
- 060.040 — `json-schema-coerce`, specified in [020.040.030](020.040.000-schema-validation.md)

## Extraction discipline

Extract by moving, not by rewriting. The existing code works and is tested; a
rewrite during extraction mixes two kinds of change and makes a regression
impossible to attribute.

Sequence per crate:
1. Move the module to a new crate verbatim. Parent depends on it and re-exports.
2. Confirm the parent's tests pass unchanged.
3. *Then* generalize the API, add tests, and write the README.

Step 2 is the checkpoint. If the parent's tests need editing at step 2, the move
was not verbatim.

## The test

Before extracting, write the crate's README opening line. If it cannot be written
without saying "for use with Cosmos-LLM", the boundary is wrong — either the crate
is not actually generic, or it is carrying something that should stay behind.

Applied honestly, this rejects some tempting extractions. That is the point.

## What not to extract

`cosmos-llm-virtual-filesystem` is already standalone and correctly scoped.

The provider implementations stay in `cosmos-llm` — a "generic HTTP client for LLM
APIs" is not a thing anyone wants separately from the client.

`Client`, `Config`, and the `Provider` trait are the crate's reason to exist.
Extracting them would leave an empty shell.
