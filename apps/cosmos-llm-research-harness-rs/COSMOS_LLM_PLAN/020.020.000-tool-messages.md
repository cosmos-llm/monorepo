# 020.020 — Tool-result messages

**Critical path.** Without this, a tool-calling loop cannot correctly reply to any
major provider.

## Current state

```rust
pub struct Message {
    pub role: String,
    pub content: String,
}
```

`ToolCall` exists as a response type, and `CompletionResponse::tool_calls()`
returns them. But there is no way to construct the *reply* — the message carrying a
tool's result back, tagged with the call it answers.

## What providers require

**OpenAI:** a message with `role: "tool"`, `tool_call_id` matching the call, and
`content` holding the result. Also, the assistant message that *made* the calls
must be replayed with its `tool_calls` array intact — content alone is not enough.

**Anthropic:** a `user` message whose content is a `tool_result` block with
`tool_use_id`. Different shape, same requirement.

With parallel tool calls — which every current model does — omitting the ID makes
the association unrecoverable. The provider rejects the request or, worse, guesses.

## Microsteps

### 020.020.010 — Extend `Message`

```rust
#[non_exhaustive]
pub struct Message {
    pub role: String,
    pub content: String,
    /// For `role == "tool"`: the call this result answers.
    pub tool_call_id: Option<String>,
    /// For `role == "assistant"`: calls this message requested.
    pub tool_calls: Vec<ToolCall>,
    /// Optional name, used by some providers for function results.
    pub name: Option<String>,
}
```

Additive, with `Default` on the new fields, so existing construction sites keep
compiling. `Message::new`, `system`, `user`, `assistant` are unchanged.

### 020.020.020 — Constructors

```rust
Message::tool_result(call_id, content)
Message::assistant_with_tools(content, tool_calls)
```

Named constructors, so no caller has to know that "tool" is the role string or
which field pairs with which role.

### 020.020.030 — Per-provider serialization

Each provider translates the common `Message` into its wire shape. OpenAI emits
`role: "tool"` with `tool_call_id`. Anthropic emits a `user` message containing a
`tool_result` content block with `tool_use_id`.

This translation is exactly the value `cosmos-llm` adds — a consumer writing one
tool loop that works against both is the whole point of the crate.

### 020.020.040 — Round-trip requirement

`CompletionResponse` → `Message` → next request must preserve everything the
provider needs. A response with three tool calls, converted to an assistant message
and replayed, must serialize back to a request the provider accepts.

Test this explicitly per provider. It is the property that breaks silently.

### 020.020.050 — Content that is not a string

Tool results are often JSON. Providers accept a string, so serialize to string —
but do it in one place with consistent formatting, not at each call site with
whatever `to_string()` a caller reaches for.

Structured content blocks (images from tools, for instance) are a larger change.
Note as future work; the string path covers research tools.

## Verification

- Round-trip test per provider: response with parallel tool calls → messages →
  request that the provider's own fixture accepts.
- Anthropic's `tool_result` block shape matches a recorded real request.
- Existing code constructing `Message` compiles unchanged.
- A tool result without an ID, sent to a provider requiring one, fails locally with
  a clear message rather than at the API.
