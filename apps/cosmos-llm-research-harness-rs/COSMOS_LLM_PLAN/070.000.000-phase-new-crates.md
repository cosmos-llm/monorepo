# Phase 070 — New crates: `cosmos-llm-agent` and `cosmos-llm-research`

Layer 4 in [`../PLAN/005`](../PLAN/005.000.000-decomposition-principle.md). This is
the phase that makes the harness thin.

**Exit criteria:** the harness binary contains argument parsing, a TUI, and glue —
and nothing that another Cosmos-LLM consumer would want.

## Steps

- [070.010](070.010.000-agent-crate.md) — `cosmos-llm-agent`
- [070.020](070.020.000-research-crate.md) — `cosmos-llm-research`

## The split

**`cosmos-llm-agent`** — the tool-calling loop and everything around it: turn
limits, cancellation, event emission, agent definitions, permission dispatch,
concurrent tool execution. Provider-agnostic and domain-agnostic. Any agentic
consumer of Cosmos-LLM needs this, whether they are doing research, code
generation, or customer support.

**`cosmos-llm-research`** — the research vertical: methodology preamble, citation
extraction and attribution, quality metrics, the research tool set, output
composition. Built on `cosmos-llm-agent`.

## Why two, not one

The agent loop has a much wider audience than research does. Fusing them would
mean anyone wanting an agent loop pulls in citation formatting and methodology
tracking, and the natural response to that is to write their own loop instead —
which is exactly the duplication this plan exists to prevent.

It also sets up the Ruby port. `cosmos-llm-agent` is the more valuable gem;
`cosmos-llm-research` is one vertical among several that could be built on it.

## Sequencing

This phase can run *before* or *concurrently with* the harness MVP. Writing the
loop directly into the harness with the intention of extracting it later is the
worse path — extraction under time pressure produces the wrong boundary, and by
then there are callers.

Recommendation: build `cosmos-llm-agent` as its own crate from the start, even in
a rough form. The harness consumes it from day one. That way the boundary is tested
by use rather than asserted by intent.
