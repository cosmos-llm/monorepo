# Phase 010 — Providers

`cosmos-llm` has three providers: openai, anthropic, openrouter. The Ruby client
has sixteen. Closing that gap is the largest single piece of work in this plan, and
the mock provider at the front of it unblocks everything else.

**Exit criteria:** mock, google, and ollama land with wire-format tests; the
`Provider` trait supports the capabilities the harness needs; adding provider N+1
is one file.

## Order matters

Do [010.010](010.010.000-trait-review.md) before adding any provider. The trait
currently has `completion`, `models`, `stream_completion`, and
`supports_streaming`. Adding eleven implementations and *then* discovering the
trait needs embeddings means eleven edits instead of one.

Then [010.040](010.040.000-mock-provider.md), because it is what makes the rest
testable.

## What the existing three do right

Worth preserving as the pattern for the rest:

- `stream_from_response` factors the shared SSE plumbing — buffering across packet
  boundaries, `[DONE]`, partial final events — so each provider supplies only a
  `parse` closure. Anthropic's is stateful (it tracks content-block indices) and the
  `FnMut` bound accommodates that. Good design; new providers reuse it.
- `Client::new_with_base_url` covers OpenAI-compatible servers (vLLM, llama.cpp,
  Azure) without a new provider. Several of the "sixteen" collapse into this.
- `supports_streaming` reports what the provider *implements here*, not what the
  upstream API offers. Honest, and the right call.

## What needs rethinking

`Provider::completion` takes `&CompletionRequest` and returns a boxed future
borrowing `'a`. Fine for the current shape. But note the `CompletionStream` return
is `'static` while `completion` borrows — a caller who wants to spawn a completion
onto a task has to keep the request alive. Consider making both `'static` by taking
the request by value or by `Arc`.

Decide this in [010.010](010.010.000-trait-review.md), before there are fourteen
implementations to migrate.
